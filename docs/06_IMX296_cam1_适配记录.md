# IMX296 cam1 适配记录

## 功能概述

本次适配面向 `rk3588-lubancat-5io` 的 `cam1` 槽位，目标是让 IMX296 具备“默认可编译、overlay 可加载、板端具备启用入口，并且 media graph 结构与 cam1 现有模板体系一致”的最小集。

## 背景与目标

在本次修改前，仓库中已经有 `drivers/media/i2c/imx296.c` 和 `rk3588-lubancat-5io-cam1-imx296-overlay.dts`，但默认 `defconfig` 未启用 `VIDEO_IMX296`，`uEnv` 也未提供 IMX296 的注释入口。进一步板端日志还出现 `rkcif_update_sensor_info` / `Not active sensor`，说明原 overlay 通过动态创建 `imx296@1a` 并重写 `csi2_dcphy1/port@0` 的方式，存在 media graph 组织风险。最小编译验证过程中还暴露出驱动自身缺少头文件和前向声明的问题。完成 graph 修复后，板端仍出现 `rockchip-csi2-dphy0: No pixel rate control in subdev`，结合 Rockchip DPHY 代码可确认其真实依赖的是 `V4L2_CID_LINK_FREQ`，而旧版 `imx296.c` 只注册了 `PIXEL_RATE`，没有向接收端暴露固定 lane 速率。补齐 `LINK_FREQ` 后，板端进一步暴露 `imx296 1-001a: supply ovdd not found, using dummy regulator`，根因是 `dcphy1_imx296` 节点把 IO 电源写成了 `dovdd-supply`，与驱动要求的 `ovdd-supply` 名称不一致。修正 `ovdd-supply` 后，板端在默认 autosuspend 路径下还出现 `8-bit write to 0x3005 failed: -6`，而把 `power/control` 强制设为 `on` 后该错误消失，说明 `runtime PM` 触发的上电恢复时序仍偏激进。

本次目标：

- 默认 `defconfig` 可带上 IMX296 驱动。
- `rk3588-lubancat-5io-csi.dtsi` 提供 IMX296 固定模板节点和 1-lane graph endpoint。
- `cam1-imx296 overlay` 改为模板启用模式，并可正常编译叠加到 `rk3588-lubancat-5io.dtb`。
- `imx296.c` 显式提供固定 `LINK_FREQ` 控件，满足 Rockchip CSI DPHY 的起流要求。
- `dcphy1_imx296` 的 `ovdd-supply` 与驱动 regulator 名保持一致，避免退回 dummy regulator。
- 经过原始/保守两套 `imx296_power_on()` 时序对比后，当前代码树已回退到原始短延时时序，并继续结合 `stream-state[...]` 关键寄存器读回日志区分是 `runtime PM` 边界问题，还是 sensor/MIPI 实际无有效出流。
- `imx296.c` 提供可通过 `echo` 写入的 `run_mode` 节点，用于在 `FREE_RUN` 与主模式快速触发之间切换。
- `uEnv` 中有明确的 `cam1-imx296` 启用入口。

## 功能边界

- 仅处理 `rk3588-lubancat-5io` 的 `cam1`。
- 不修改其它槽位的 sensor 选择逻辑。
- 不执行整包镜像烧录。
- 不直接验证真实板端采图链路。
- 不在本轮实现 `XMASTER=High` 的真正 slave/外触发模式。

## 架构与模块关系

`rk3588-lubancat-5io-csi.dtsi` 负责提供 `cam1` 的公共 CSI 拓扑、Rockchip ISP/CIF 链路，以及 IMX296 的固定模板节点和 1-lane graph endpoint。

`rk3588-lubancat-5io-cam1-imx296-overlay.dts` 负责：

- 只开启 `&i2c1`，不再动态创建 `imx296@1a`。
- 将 `&dcphy1_imx296` 置为 `status = "okay"`。
- 将 `&gd32_mcu` 置为 `status = "okay"`，把 `0x2a` 的辅助 MCU 正式纳入 I2C 设备模型。
- 使能 `mipi1_csi2`、`rkcif_mipi_lvds1`、`rkisp1`、`rkisp1_vir0`。
- 显式将 `&dcphy1_imx415` 压为 `disabled`，避免同槽位两个传感器同时激活。

当前 IMX296 节点默认保留 `rockchip,camera-module-sync-mode = "internal_master"` 和 `trigger-mode = <0>`，用于匹配当前驱动已经支持的 master/free-run 路线。

当前 `imx296.c` 还负责向上游媒体栈暴露：

- `PIXEL_RATE`，供 ISP/CIF 估算数据率。
- 固定的 `LINK_FREQ`，供 Rockchip CSI DPHY 配置 lane 速率。
- 当前回退为原始短延时 `power_on` 时序，用于继续对比 `runtime PM` 相关现象；`stream-state[...]` 日志用于补足软件侧证据。
- `run_mode` sysfs 节点，供板端通过 `echo` 切换 `FREE_RUN` / 主模式快速触发。

当前 `dcphy1_imx296` 节点的三路电源属性应为：

- `avdd-supply`
- `ovdd-supply`
- `dvdd-supply`

## 调用链分析

1. U-Boot 根据 `uEnvLubanCat5IO.txt` 读取 `dtoverlay` 条目。
2. 若启用 `rk3588-lubancat-5io-cam1-imx296-overlay.dtbo`，overlay 叠加到 `rk3588-lubancat-5io.dtb`，开启 `i2c1`、启用 `&dcphy1_imx296`、启用 `&gd32_mcu`，并关闭 `&dcphy1_imx415`。
3. Kernel 启动后，I2C core 在 `i2c1` 上枚举 `compatible = "sony,imx296lq"` 的模板节点。
4. `imx296_probe()` 申请时钟、电源、GPIO，并注册 V4L2 子设备及其 `LINK_FREQ` / `PIXEL_RATE` 控件。
5. Rockchip CSI DPHY 通过 `V4L2_CID_LINK_FREQ` 获取单 lane MIPI 速率，完成接收端配置。
6. Rockchip CIF/ISP 通过 `dcphy1_in_imx296 -> csi2_dcphy1 -> mipi1_csi2 -> rkcif_mipi_lvds1 -> rkisp1_vir0` 链路接入。

## 编译与部署

### 宿主机最小编译验证

```sh
./scripts/config --file .config -e VIDEO_IMX296
make ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- olddefconfig
make ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- drivers/media/i2c/imx296.o
```

### overlay 语法与叠加验证

```sh
cpp -nostdinc -I include -I arch/arm64/boot/dts -undef -x assembler-with-cpp \
  arch/arm64/boot/dts/rockchip/overlay/rk3588-lubancat-5io-cam1-imx296-overlay.dts \
  | dtc -@ -I dts -O dtb -o /tmp/rk3588-lubancat-5io-cam1-imx296-overlay.dtbo -

cpp -nostdinc -I include -I arch/arm64/boot/dts -undef -x assembler-with-cpp \
  arch/arm64/boot/dts/rockchip/rk3588-lubancat-5io.dts \
  | dtc -@ -I dts -O dtb -o /tmp/rk3588-lubancat-5io-symbols.dtb -

fdtoverlay -i /tmp/rk3588-lubancat-5io-symbols.dtb \
  -o /tmp/rk3588-lubancat-5io-imx296-merged.dtb \
  /tmp/rk3588-lubancat-5io-cam1-imx296-overlay.dtbo
```

- `defconfig` 已补 `CONFIG_VIDEO_IMX296=y`
- `rk3588-lubancat-5io-csi.dtsi` 已包含 `dcphy1_imx296` 模板和 `dcphy1_in_imx296` 1-lane endpoint
- `drivers/media/i2c/imx296.c` 在当前 5.10 树可编译为对象文件
- `drivers/media/i2c/imx296.c` 已包含固定 `V4L2_CID_LINK_FREQ` 控件
- `drivers/media/i2c/imx296.c` 当前已回退为原始 `power_on` 时序，同时保留 `stream-state[...]` 读回日志
- `drivers/media/i2c/imx296.c` 已新增 `run_mode` sysfs 节点，复用现有模式切换逻辑支持 `echo` 写入
- `drivers/media/i2c/imx296.c` 已新增 `stream on` 前后关键寄存器读回日志，用于定位 sensor 是否真正进入输出态
- `rk3588-lubancat-5io-cam1-imx296-overlay.dts` 可编译为 `dtbo`
- `cam1-imx296 overlay` 可叠加到 `rk3588-lubancat-5io.dtb`
- 合并后 DT 中 `dcphy1-imx296@1a` 为 `status = "okay"`，`dcphy1-imx415@1a` 为 `status = "disabled"`
- 合并后 DT 中 `gd32-mcu@2a` 可被 IMX296 overlay 置为 `status = "okay"`
- 合并后 `dcphy1_in_imx296` 为 1-lane (`data-lanes = <0x01>`)
- 合并后 `dcphy1-imx296@1a` 已使用 `ovdd-supply`

## 风险点

- 合并后的 DT 中仍会保留 `dcphy1-imx415@1a` 这个 disabled 模板节点，因此 `dtc` 仍会报重复 unit-address 警告；这属于当前 vendor DTS 组织方式的已知现象，不等于两个 active 节点同时 probe。
- 真正是否能稳定出流，仍受硬件连线、电源时序、MIPI 1-lane 带宽、板端加载顺序影响。
- 当前 `imx296.c` 仍以 `internal_master` 为主路径，若后续恢复 `XMASTER=High` 的 slave/外触发方案，还需单独适配驱动与 DT。
- 主模式快速触发虽然已经可通过 `run_mode` 切换，但板级 `XMASTER` / 外部触发脉冲若不匹配，切换后仍可能看起来“黑屏”。
- 本次 `LINK_FREQ` 修复只解决 Rockchip DPHY 速率查询缺口；若重新烧录后仍黑屏，就需要继续分层排查 sensor 实际出流、板端光路和应用打开节点是否正确。
- 本次 `ovdd-supply` 修复仅解决 DTS 属性名与驱动 regulator 名不一致的问题；若板端硬件实际没有提供正确的 IO 电源，仍可能继续黑屏。
- 当前已回退原始 `power_on` 时序，`0x3005`/`-ENXIO` 类边界问题可能重新出现；若在原始时序下仍保持 `stream-state[...]` 显示 sensor 已退出 `standby` 且 `test_pattern` 已生效、但 `frame dma end` 仍为 0，则主因更偏向 sensor/MIPI 输出层或板级 DPHY 接收。

## 已知问题

- `rk3588-lubancat-5io-csi.dtsi` 顶部 `cam1` 链路注释与真实 endpoint 指向不一致，真实链路应为 `rkisp1_vir0`；该问题不影响本次最小修复，但会影响后续阅读体验。
